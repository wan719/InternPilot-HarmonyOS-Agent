## 阶段 2：从纯 mock 到可解释的技术闭环

时间：2026-07-11 ～ 2026-07-15

目标：在不破坏最小 Demo 的基础上，补一个可解释的工程亮点。

### A. 首选：后端轻接口 + mock fallback

实现最小后端接口：

```text
POST /api/c4/analyze
```

请求示例：

```json
{
  "job": {
    "title": "鸿蒙应用开发实习生",
    "company": "示例科技公司",
    "description": "岗位 JD 文本"
  },
  "candidate": {
    "target": "鸿蒙应用开发实习",
    "skills": ["Java", "Vue", "ArkTS"],
    "experience": "InternPilot 项目经历摘要"
  }
}
```

响应示例：

```json
{
  "matchScore": 82,
  "summary": "整体匹配度较高，但需要补充鸿蒙端项目证明。",
  "strengths": ["已有完整 Web 项目经历", "具备 Java 和前端基础"],
  "gaps": ["ArkTS 经验需要项目证明", "简历量化表达不足"],
  "actions": [
    {
      "title": "补充 HarmonyOS Demo 截图",
      "priority": "high",
      "dueDate": "今天"
    }
  ],
  "reminders": [
    {
      "title": "晚上复查 Demo 是否稳定",
      "time": "今天 20:00"
    }
  ]
}
```

要求：

- 接口可以先返回固定 mock JSON。
- 客户端请求失败时仍回退到本地 mock。
- 演示时可以解释：网络 / AI 不可用时，fallback 保证 Demo 不断链。

### B. 次选：系统通知能力

若后端联调卡住，则先做 HarmonyOS 通知能力：

- 请求通知权限。
- 根据 mock `reminders` 创建通知。
- 权限失败时展示页面内提醒。
- 演示时强调使用了鸿蒙终端能力。

## 七、技术路线

```text
HarmonyOS / ArkTS 客户端
├── 首页
├── 岗位与个人背景输入
├── 分析结果展示
├── 今日任务展示
├── 页面内提醒 fallback
└── 系统通知能力（可选增强）
        │
        │ HTTP / fallback
        ▼
backend-c4 轻接口
└── POST /api/c4/analyze
        │
        ├── 固定 mock JSON
        └── 后续可替换 AI 分析服务
```

技术解释重点：

- 为什么先做本地 mock：保证 Demo 不受网络和模型服务影响。
- 为什么保留 fallback：比赛演示最怕现场断链，fallback 是工程可靠性设计。
- 为什么不迁移完整平台：初赛重点是核心闭环和创新表达，不是功能堆砌。
- 为什么适合当前能力结构：原 InternPilot 有求职场景和 AI 分析基础，HarmonyOS 端提供新的终端入口和提醒能力。

## 八、风险控制

### 最大风险 1：需求膨胀

任何新功能都必须回答：

> 它是否直接帮助初赛演示闭环？

如果答案不是明确的“是”，就延后。

### 最大风险 2：DevEco / ArkTS 环境卡住

控制方式：

- 保留最小 Demo 分支。
- 不在同一天同时改 UI、后端、通知。
- 遇到红色编译错误，先修第一条错误。
- 不删除可运行版本。

### 最大风险 3：材料来不及

控制方式：

- 7 月 15 日必须开始文档。
- 7 月 20 日前必须有第一次上传测试。
- 7 月 26 日不能作为主要完成日。

### 最大风险 4：本人无法解释 AI 生成代码

控制方式：

- 每次合并前写清楚“做了什么”。
- 核心文件至少自己读一遍。
- 演示脚本里只讲自己能解释的实现。
